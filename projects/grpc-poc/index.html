gRPC + Envoy Service Mesh POC

Production-grade gRPC service mesh using Envoy as a sidecar proxy to expose gRPC services as HTTP+JSON. Explores service-to-service communication patterns at scale.

Overview

A proof-of-concept demonstrating how to run a gRPC service behind an Envoy proxy that translates HTTP/JSON requests to gRPC — enabling REST clients to communicate with gRPC backends without any client-side gRPC library.

Born out of experience building microservices at Flipkart and CRED, where service mesh patterns are critical for reliability at scale.

Problem

gRPC is excellent for service-to-service communication — strongly typed, efficient binary serialization, bidirectional streaming. But it's incompatible with standard REST clients and browsers. The transcoding pattern (Envoy as a sidecar handling protocol translation) solves this cleanly.

Architecture

REST Client → Envoy (HTTP/JSON ↔ gRPC transcoding) → Java gRPC Service

Envoy is configured with grpc-http1.1-bridge and grpc-json-transcoder filters. The proto descriptor is compiled and passed to Envoy at startup so it knows how to map REST endpoints to RPC methods.

Key Learnings

  • Proto-first design matters. The .proto file is the contract. Changes cascade to both Envoy config and the Java service — same discipline as schema-first API design.
  • Envoy's static config is verbose for local dev but the xDS API investment pays off at scale (we use similar patterns at CRED for service discovery).
  • gRPC status codes ≠ HTTP status codes. Envoy handles mapping but you need to understand it for debugging. UNAVAILABLE → 503, NOT_FOUND → 404, etc.
  • Proto descriptor files must be precompiled and baked into Envoy config — a footgun if your CI doesn't automate it.
